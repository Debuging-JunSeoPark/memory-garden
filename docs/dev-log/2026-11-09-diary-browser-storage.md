# 2026-11-09 프론트엔드 개발일지 — 날짜별 일기 저장과 다시 열기

정원 입구의 일기장에서 날짜·제목·본문·사진과 설명을 저장할 수 있게 했다. 페이지를 새로고침한 뒤 같은 날짜를 선택하면 기록이 복원된다. 같은 날짜에서 글을 바꾸거나 사진을 삭제한 뒤 저장하면 그 날짜의 기록이 갱신된다. 오늘 작업은 [Issue #22](https://github.com/Debuging-JunSeoPark/memory-garden/issues/22)에서 추적한다.

## 저장 단위와 기술 선택

| 선택지 | 검토한 점 |
| --- | --- |
| localStorage | 문자열을 저장하므로 사진을 별도로 변환해야 한다. 파일이 큰 경우 인코딩과 동기 쓰기가 입력 흐름에 부담을 줄 수 있다. |
| IndexedDB | 브라우저에서 File과 텍스트를 함께 구조화 복제하고, 한 트랜잭션으로 기록을 교체할 수 있다. |
| 서버 저장 | 기기 간 접근에 적합하다. 인증, 사용자별 권한, 이미지 저장소와 실패 복구가 필요해 후속 단계로 다룬다. |

IndexedDB를 선택했다. 기록 날짜를 키로 쓰고, 한 날짜의 제목·본문·사진 목록·설명을 하나의 레코드로 저장한다. 같은 키에 저장하면 한 번의 쓰기로 전체 기록을 갱신한다. 삭제한 사진은 다음 저장에서 해당 기록에서 빠진다. 사진 미리보기용 object URL은 화면에 표시할 때 다시 만든다.

## 입력과 비동기 상태

정원 위젯은 작성 화면을 열었는지와 정원으로 돌아가는 동선을 관리한다. 날짜 선택, 초안, 읽기와 저장 상태는 일기 기능 내부로 옮겼다. 작성 화면을 닫았다 열어도 유지하고, 날짜별 초안을 현재 페이지 세션에 보관해 다른 날짜로 이동해도 쓰던 글과 사진을 되찾을 수 있게 했다.

선택 날짜를 읽는 동안 해당 날짜의 편집과 저장을 막는다. 조회가 실패하면 다시 불러올 수 있으며, 조회에 실패한 날짜를 빈 일기로 덮어쓰는 경로를 차단했다. 날짜를 빠르게 이동하면 이전 조회의 늦은 응답은 현재 화면에 반영하지 않는다. 사진을 검사하는 동안 날짜 변경과 저장을 막아, 아직 검사 중인 사진이 다른 날짜에 붙거나 저장에서 빠지는 상황을 피했다.

본문의 공백을 검사하고, 저장 완료는 IndexedDB 요청의 성공 이벤트가 아니라 트랜잭션 완료 이벤트에서 판단한다. 요청이 성공한 뒤에도 트랜잭션이 중단될 수 있기 때문이다. 저장 실패를 알리고 초안을 그대로 남겨 재시도할 수 있게 했다. 작업마다 데이터베이스 연결을 닫고, 스키마 변경 요청이 오면 이전 연결을 닫도록 처리했다.

## 검증

- 기존 구현에 새 브라우저 테스트를 실행해 저장 버튼이 없어 실패하는 것을 확인했다.
- `pnpm check`에서 포맷·린트·타입 검사, Node 테스트 25개, 저장소 검증과 프로덕션 빌드가 통과했다.
- `pnpm test:e2e`는 데스크톱·모바일 Chromium 합계 22개가 통과했다. 날짜별 저장, 새로고침 뒤 글·사진 복원, 실제 이미지 해독, 날짜 왕복 초안 보존, 사진 삭제와 수정 저장을 확인했다.
- 쓰기 요청이 성공한 직후 트랜잭션을 강제로 중단했다. 완료 안내 대신 실패 안내가 나오고 글과 저장 재시도 버튼이 남는지 확인했다. 공백뿐인 본문도 검사했다.

## 통합과 후속 작업

전날 개발일지 PR #15는 필수 검사를 통과한 뒤 Squash 병합했다. 일기 저장 작업은 병합 커밋 `56a6fc8`에서 별도 브랜치로 시작했다.

저장 범위는 같은 브라우저의 같은 사이트 주소다. 브라우저에서 사이트 데이터를 지우면 저장한 일기도 삭제된다. 동시에 여러 탭에서 같은 날짜를 저장하면 마지막으로 완료된 쓰기가 남는다. 다음 단계는 저장 날짜를 정원의 일별 꽃과 책장의 월별 책에 연결하고 같은 날을 수정해도 꽃이 중복되지 않게 하는 것이다.
