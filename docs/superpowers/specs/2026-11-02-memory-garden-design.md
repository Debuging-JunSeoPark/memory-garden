# 기억의 정원 제품 및 저장소 설계

## 의도

기억의 정원은 사용자가 작은 3D 정원을 직접 걸어 다니며 하루의 글과 사진을 기록하고, 여러 날짜의 기록을 골라 블로그 글 초안을 만드는 웹 서비스다. 일반적인 생산성 도구의 달력 화면보다 게임을 플레이하는 감각을 앞세운다. 기록은 정원의 꽃, 오브젝트, 공간 변화로 남고 달력은 기록을 찾고 조합하는 보조 수단으로 사용한다.

## 목표

- 사용자가 Google 계정으로 로그인하고 여러 기기에서 같은 기록을 이어서 본다.
- 캐릭터를 움직여 일기장이나 기억 오브젝트와 상호작용한다.
- 날짜별 글과 여러 이미지를 저장하고 수정한다.
- 기록한 날짜와 정원 성장 상태를 월간 달력에서 확인한다.
- 여러 날짜를 선택해 사실에 기반한 블로그 초안을 생성한다.
- 작은 Issue, 작업 브랜치, PR, 자동 검사, Squash Merge 흐름을 처음부터 지킨다.

## 범위 밖

- 첫 버전에서 다른 사용자와 정원을 방문하거나 실시간 멀티플레이를 제공하지 않는다.
- 첫 버전은 기본 캐릭터 한 명으로 시작한다. 캐릭터 외형 해금은 이후 성장 기능과 함께 검토한다. 아이템 상점, 재화, 퀘스트 시스템은 첫 버전 범위에서 제외한다.
- 네이버 블로그나 다른 플랫폼에 자동 게시하지 않는다. 초안 편집과 복사까지만 제공한다.
- 모바일 네이티브 앱을 별도로 만들지 않는다.

## 피해야 할 결과

- 생성형 이미지 한 장을 배경으로 두고 게임처럼 보이게만 만드는 화면
- 기록을 연속으로 쓰지 않았을 때 불이익이나 실패감을 주는 설계
- 일기에 없는 사건을 AI가 사실처럼 추가하는 초안
- 달력, 게임 화면, 작성 화면이 서로 관계없는 기능처럼 분리되는 구조
- 큰 기능과 리팩터링을 한 PR에 섞거나 자동 검사를 통과하지 않은 채 병합하는 운영

## 제품 경험

### 정원 화면

로그인 후 정원 화면이 홈이 된다. 사용자는 키보드와 화면 조작으로 캐릭터를 이동한다. 빛나는 일기장에서는 오늘 기록을 작성하고, 꽃밭과 기억 오브젝트에서는 이전 기록을 연다. 모든 오브젝트와 지형은 Three.js 장면으로 만들며, 생성형 이미지를 화면 배경으로 사용하지 않는다. 초기 버전은 로우 폴리와 손으로 빚은 듯한 재질을 사용하고 모델 수를 제한한다.

처음에는 작은 야외 정원에서 시작한다. 캐릭터가 돌길 끝의 책장에 가까워지면 3D 선반을 살펴볼 수 있다. 첫 칸의 정원 안내서는 펼친 책 형태로 읽는다. 실제 기록을 연결하면 일기를 쓴 달마다 책 한 권이 생기고, 정원에는 기록한 날짜마다 꽃 한 송이가 남는다. 같은 날의 수정은 새 꽃을 만들지 않는다.

정원은 성장 단계마다 사용자가 화단, 연못, 나무 그늘처럼 풍경을 바꾸는 요소를 골라 서로 다른 모습으로 키운다. 자동으로 지급되는 기록 보상과 사용자가 고른 정원 요소를 구분하며, 성장 단계의 기준과 선택지는 일기 저장과 연결하는 작업에서 정한다.

### 기록 작성

날짜, 본문, 선택적 제목, 여러 이미지를 저장한다. 이미지 업로드 상태와 실패를 명확히 보여준다. 기록을 저장하면 해당 날짜의 정원 오브젝트와 성장 수치가 바뀐다. 며칠 기록하지 않아도 기존 정원은 시들거나 줄어들지 않는다.

기록 날짜는 브라우저에서 감지한 IANA 시간대를 프로필에 저장하고 그 시간대의 달력 날짜로 계산한다. 사용자는 설정에서 시간대를 바꿀 수 있으며, 이미 저장된 기록 날짜는 자동으로 이동하지 않는다.

### 달력

달력은 정원 화면에서 열리는 게임 UI 패널이다. 기록이 있는 날짜에는 씨앗이나 작은 꽃 표시가 나타난다. 날짜를 누르면 기록을 읽고 수정하며, 선택 모드에서는 여러 날짜를 골라 블로그 초안 생성을 시작한다.

### 블로그 초안

선택한 기록의 본문과 이미지 설명을 서버에서 정리해 AI 모델에 전달한다. 사용자는 글의 분위기와 길이를 선택할 수 있다. 생성 결과는 편집 가능한 초안으로 저장한다. 프롬프트에는 제공된 기록 밖의 사건을 만들지 말라는 제약과 날짜별 출처를 포함한다.

선택한 기록은 날짜순으로 정렬한다. 초안 생성 시 이미지를 서버에서 축소하고 멀티모달 모델로 분석해 글과 함께 사용한다. 생성 화면에서 이미지가 외부 AI 처리에 사용된다는 사실을 알리고, 사용자가 이미지 분석을 끌 수 있게 한다. 생성된 초안 본문은 당시 입력의 스냅샷이며 이후 원본 일기가 수정되어도 자동으로 바뀌지 않는다.

## 기술 설계

### 애플리케이션

- Next.js 16 App Router, React 19, TypeScript strict
- Tailwind CSS v4
- React Three Fiber와 Drei를 이용한 Three.js 정원
- TanStack Query는 서버 상태 캐시가 필요한 클라이언트 상호작용에 사용
- Zustand는 캐릭터 위치, 열린 패널, 선택한 날짜 같은 게임 UI 상태에만 사용
- Feature-Sliced Design의 `app → widgets → features → entities → shared` 의존성 규칙 준수

### 백엔드

- Next.js Route Handlers와 Server Actions를 BFF 및 서버 계층으로 사용
- Supabase PostgreSQL을 영구 데이터베이스로 사용
- Supabase Auth의 Google OAuth 사용
- Supabase Storage에 일기 이미지를 저장하고 사용자별 비공개 경로 및 서명 URL 사용
- Row Level Security로 자신의 기록, 이미지, 초안만 접근하도록 제한
- OpenAI Responses API를 서버에서 호출해 블로그 초안 생성
- Zod로 서버 입력과 AI 구조화 응답 검증

작은 폼 변경에는 Server Actions를 사용하고, 이미지 업로드·서명 URL·AI 생성에는 Route Handlers를 사용한다. 모든 도메인 작업은 FSD 슬라이스의 공개 API를 통해 노출한다.

배포는 Vercel과 Supabase 관리형 서비스를 기준으로 한다. AI 모델명은 환경 변수로 분리하고 구현 시점의 공식 지원 멀티모달 모델을 선택한다. 한 번에 최대 14일, 이미지 30장, 정규화한 본문 30,000자를 허용한다. 사용자당 하루 5회 생성을 기본 한도로 두며 첫 버전은 진행 상태를 표시하는 동기 요청으로 구현한다. 배포 환경의 실행 제한을 넘기면 작업 테이블과 비동기 상태 조회 방식으로 전환한다.

별도 NestJS 서버는 첫 버전에서 만들지 않는다. 독립 서버가 필요한 배치 작업, 다수 외부 클라이언트, 복잡한 도메인 로직이 생길 때 API 경계를 유지한 채 분리한다.

### 3D 상호작용 기준

- 고정된 아이소메트릭 카메라와 제한된 보행 영역을 사용한다.
- 첫 버전의 충돌은 단순 경계 상자와 원형 범위로 처리한다.
- 데스크톱은 WASD/방향키와 Enter 또는 상호작용 키를 제공한다.
- 모바일은 가상 조이스틱과 별도 상호작용 버튼을 제공한다.
- 모션 감소 설정을 존중한다. WebGL을 사용할 수 없는 환경에서는 정적 지도로 자동 전환하고, 지도에 표시된 책장을 통해 같은 안내서와 기록 기능을 제공한다.

### 테스트 기준

- Vitest와 Testing Library로 도메인 규칙, 폼, 달력 선택, 상태 전환을 검증한다.
- Playwright는 로그인 없이 확인 가능한 셸과 핵심 내비게이션에 한해 작은 스모크 테스트를 둔다.
- Three.js 장면의 픽셀 결과를 그대로 복제하는 테스트는 만들지 않고 상호작용 규칙과 접근 가능한 대체 UI를 검증한다.

### 핵심 데이터

- `profiles`: 사용자 공개 이름, IANA 시간대, 생성 시각
- `diary_entries`: 사용자, 기록 날짜, 제목, 본문, 생성·수정 시각
- `diary_images`: 기록, 저장소 경로, 순서, 대체 텍스트, 크기
- `garden_states`: 사용자, 성장 레벨, 잠금 해제 오브젝트, 장면 버전
- `blog_drafts`: 사용자, 스타일, 제목, 본문, 생성 시각
- `blog_draft_sources`: 초안, 기록, 날짜순 순서

`diary_entries`는 사용자와 기록 날짜 조합을 유일하게 만들어 하루에 하나의 기본 기록을 유지한다. 여러 사건을 따로 기록할 필요가 확인되면 후속 버전에서 구조를 확장한다.

프로필은 표시와 지역 설정만 소유하고 모든 성장 데이터는 `garden_states`가 소유한다. 첫 기록 저장 시 그 날짜에 대한 성장 포인트를 한 번 지급한다. 이후 수정은 포인트를 추가하지 않으며, 이미지는 같은 날의 시각적 변형에만 영향을 준다. 삭제하더라도 이미 자란 정원과 잠금 해제 항목은 되돌리지 않는다.

일기와 이미지는 30일 동안 복구 가능한 소프트 삭제를 기본으로 한다. 복구 기간이 지난 항목은 정기 정리 작업에서 데이터와 저장소 객체를 함께 제거한다. 초안은 삭제된 원본의 내용을 복제해 보관하지 않고 출처 링크를 사용할 수 없음으로 표시한다.

이미지는 JPEG, PNG, WebP를 허용하고 파일당 10MB, 기록당 10장으로 제한한다. 클라이언트 미리보기와 업로드 진행률을 제공하며 서버에서도 MIME, 크기, 소유권을 검증한다. 비공개 객체 경로는 사용자와 기록 ID를 포함하고 서명 URL은 짧은 만료 시간을 사용한다. 실패한 업로드와 삭제된 기록의 고아 객체는 정리 작업에서 제거한다.

## 구현 접근 방식

### 고려한 방식

1. **Next.js 풀스택 + Supabase — 선택**
   인증, 데이터베이스, 이미지 저장소를 빠르게 구성하면서 서버 전용 AI 호출과 RLS를 유지한다. 한 저장소에서 제품을 작게 나누어 개발하기 좋다.

2. **Next.js + NestJS + PostgreSQL**
   백엔드 경계와 학습 경험은 명확하지만, 첫 제품부터 인증·배포·파일 저장·API 계약을 두 앱에서 관리해야 한다. 현재 범위에는 운영 비용이 크다.

3. **Firebase 중심 구조**
   인증과 저장소 시작은 빠르지만 날짜별 기록, 초안과 기록 관계, 향후 검색에는 관계형 PostgreSQL이 더 자연스럽다.

## GitHub 운영

- 공개 저장소 이름: `memory-garden`
- 기본 브랜치: `main`
- 작업 브랜치: `feat/<topic>`, `fix/<topic>`, `refactor/<topic>`, `docs/<topic>`, `chore/<topic>`
- 커밋: Conventional Commits 사용. 예: `feat: add diary calendar selection`
- Issue 하나는 사용자에게 설명 가능한 한 가지 결과를 다룬다.
- PR은 한 Issue를 해결하고, 본문에 `Closes #번호`를 포함한다.
- 병합 방식은 Squash Merge를 기본으로 하고 브랜치를 자동 삭제한다.
- `main` 직접 푸시는 금지하고 PR과 필수 검사를 요구한다.
- CI 필수 검사: format check, lint, type-check, test, build
- PR에는 변경 이유, 동작, 확인 방법, 화면 변경 이미지, 남은 위험을 기록한다.
- Dependabot은 주간 단위로 묶어서 실행한다.

첫 커밋은 저장소 운영 문서와 빈 애플리케이션 기반을 함께 담지 않는다. `docs: establish project conventions`와 `build: initialize next app`을 분리해 이력의 의도를 명확히 한다.

## 저장소 문서와 자동화

- `README.md`: 제품 소개, 로컬 실행, 환경 변수, 명령어

- `.github/workflows/ci.yml`: pnpm 기반 필수 검사
- `.github/dependabot.yml`: npm 및 GitHub Actions 업데이트
- `.editorconfig`, `.nvmrc`, pnpm 버전 고정
- Husky와 lint-staged로 커밋 전 포맷 및 린트 검사
- commitlint로 커밋 메시지 검사

## 에이전트 하네스

저장소는 사람과 코딩 에이전트가 같은 규칙과 진행 상태를 공유할 수 있는 작은 하네스를 포함한다. 하네스는 프로젝트 코드에 대한 무제한 실행 권한을 부여하지 않으며, 저장소 안에 명시한 입력·출력 계약과 허용된 훅만 실행한다.

- `agents/memories/repo.md`: 오래 유지되는 제품 선호, 아키텍처 결정, 저장소 규칙
- `agents/memories/session.md`: 현재 목표, 완료 항목, 다음 작업, 알려진 장애물
- `agents/skills/`: 한 가지 작업을 입력과 출력 계약으로 정의하는 재사용 가능한 로컬 스킬
- `agents/hooks/allowlist.json`: 실행 가능한 훅과 명령 인자 범위
- `agents/hooks/runner.js`: 허용 목록을 검증한 뒤 훅을 실행하는 러너
- `agents/hooks/examples/`: 부작용이 제한된 예제 훅
- `agents/server-agent/`: 인증된 로컬 작업 위임 API의 스캐폴드. 첫 버전은 외부 배포하지 않는다.
- `docs/harness.md`: 구조, 신뢰 경계, 보안 가드레일
- `docs/harness-usage.md`: 사람과 에이전트가 하네스를 사용하는 절차와 예시

기억 파일에는 비밀값, 개인정보, 토큰, 원문 일기 데이터를 기록하지 않는다. `session.md`는 커밋 가능한 공개 진행 상태만 담고 개인 메모나 로컬 환경 상태는 별도 무시 파일에 둔다. 훅 러너는 셸 문자열을 평가하지 않고 등록된 실행 파일과 고정 인자만 `spawn`으로 호출한다. 서버 에이전트는 기본적으로 localhost에만 바인딩하고 인증 토큰, 요청 크기 제한, 작업 종류 허용 목록, 타임아웃, 감사 로그 인터페이스를 갖춘다.

1. 독립 Git 저장소와 GitHub 저장소 생성, 운영 문서 및 템플릿 추가
2. Next.js 프로젝트와 품질 도구 초기화
3. Supabase 프로젝트 연결과 Google 로그인
4. 기록 CRUD 및 이미지 업로드
5. 코드 기반 3D 정원과 캐릭터 이동, 기록 상호작용
6. 게임 UI 형태의 달력과 날짜 선택
7. AI 블로그 초안 생성, 편집, 복사
8. 접근성, 모바일 조작, 성능 및 오류 상태 개선
